## Checksum verification pass (2026-11-09)
- Design: after a download finishes, the file is hashed streaming (64 KiB chunks, `tokio::task::spawn_blocking`, task lock released while hashing) and compared with the expected hash. Priority: user-entered SHA-256 (Add URL modal + confirmation popup, "Expected SHA-256 (optional)") > `Digest` / `Content-Digest` header (RFC 3230/9530, `SHA-256=<base64>` / `MD5=`, base64 decoded to hex) > `Content-MD5` > sidecar `<url>.sha256` / `<url>.md5` via plain GET (bare hash or `<hash>  <filename>`, filename match wins; one shared 5 s timeout, best-effort, never holds the task lock). No source -> completed + verify_state "unavailable" (grey dash); never failed for lacking a hash.
- Match -> "verified" (lime check + first 12 hex, full hash in tooltip) under the status pill. Mismatch -> status failed, error "checksum mismatch (expected ……, got ……)", file kept on disk, desktop notification "Checksum tidak cocok: <file> — expected … got …" via notify.rs (title special-cased on the error prefix), Retry re-downloads and verifies again. `verify_checksum(id)` command + Verify row action (completed rows with a stored hash, failed mismatch rows); re-verifying a repaired file flips it back to completed and clears the error.
- Persistence: `downloads.db` gains `expected_hash` / `computed_hash` / `verify_state` columns via `ALTER TABLE ... ADD COLUMN` (errors ignored, old DBs keep working); sidecar JSON carries the same three fields and wins on resume/restore. `sha2` moved from dev-dependencies to dependencies; `md5 = "0.7"` + `base64 = "0.22"` added. API gotchas found while building: md5 0.7 has no `Md5` Digest hasher — use `md5::Context::consume` + `compute`; the `http` crate has no `CONTENT_MD5` constant — use the string name `"content-md5"`.

## Daily schedule pass (2026-11-09)
- Design: new `src-tauri/src/schedule.rs` (pure logic, injected clock). `DailySchedule { enabled, start/stop "HH:MM", days[7] Mon..Sun }` in Settings (serde default: disabled, 23:00–06:00, all days; old settings.json loads; malformed times normalised to defaults). `contains()` handles overnight windows (after-midnight part belongs to the start day) and start==stop = whole day. `next_event()` scans yesterday..+7 days so a window that started yesterday and ends today is found; `next_label()` gives "Queue starts today 23:00" / "Queue stops tomorrow 06:00" / "Queue starts Mon 09:00".
- Engine: `Manager::schedule_tick(now)` runs from `queue_loop` every 60th tick (~30 s, before `queue_tick` so a Stop prevents starting in the same tick). In window + stopped -> Start; out of window + running -> Stop (caller pauses via new `pause_all_tasks_scheduled`). A manual Start/Stop or a pending one-shot sets `schedule_hold`, cleared at the next window boundary or when the one-shot fires — the scheduler never fights a deliberate action mid-window. One-shot `schedule_queue` keeps working (hold while pending).
- Resume correctness (found while writing the integration test): `queue_tick` only started "queued" tasks, so a scheduler-paused download would never resume. New `TaskInner.paused_by_schedule` (runtime-only, never persisted; restored tasks stay paused after a restart): `pause_task_scheduled` sets it, `queue_tick` also starts paused+flagged tasks, `start_task` clears it. A manual pause stays paused.
- REAL BUG FOUND by the schedule integration test (pre-existing, not schedule code): the speed limiter wedged forever. `RateLimiter::acquire` called `try_take(n)` with the full `n` on every retry while `try_take` deducted partial takes — for a chunk bigger than the one-second token cap (localhost delivers 229–255 KiB chunks; cap at 200 KiB/s is 204800 B) the loop recomputed the same ~1.1 s wait forever and downloaded bytes froze (observed: 196608 B then nothing for 90 s). Fix: `try_take` deducts only on success (a wait deducts nothing) and `acquire` splits requests into steps <= the token cap. Regression tests: `try_take` wait-does-not-consume, `acquire` of 2 KiB at 1 KiB/s, 8 concurrent acquires. Note: any speed-limited download with large chunks or several workers could have hit this before; no-limit downloads were unaffected (limit 0 short-circuits).
- UI: Settings section "Daily schedule" after the one-shot row (Enabled switch, From/To time inputs, Mon–Sun toggle pills, next-event line, honesty note "Only while ZDM is running — it does not start the app by itself"), plus the same next-event line in the Downloads toolbar (`#schedule-line`, shown only when enabled). New `get_schedule_status` command; frontend refreshes it on load/save and every 2 s poll. Settings form round-trips the schedule via existing `save_settings`.
